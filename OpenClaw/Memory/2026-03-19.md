## PBX6000 NVMe 首启问题 - Codex 深度分析

### 问题现象
清 CMOS 后首轮找不到 NVMe，warm reset 后能找到

### 核心结论
`PciBus.c` 枚举顺序和 `Bds.c` reset 链组合导致：
- `EnumerateBus()` 先扫子总线，后做 PCIe link 初始化
- 首轮冷起时链路还没稳，config read 返回 0xFFFFFFFF → 判定无设备
- warm reset 后链路稳定，才能扫到

### BDS Reset 链机制
代码位置: `AmiModulePkg/Bds/Bds.c`
- 1643-1649: `PreviousMemoryTypeInformation` 不存在 → `IsFirstBoot=TRUE`
- 1767-1778: runtime memory type 变化 → `ResetRequired=TRUE`
- 1809-1825: 写 CMOS `0x66=1` → `EfiResetCold`
- 1828-1836: 发现 `0x66==1` → 清零 → `EfiResetWarm`

### PciBus 枚举时序
代码位置: `AmiModulePkg/PCI/PciBus.c`
- 6943-6992: 首次 config read (只有 CRS/slot implemented 场景重试)
- 7413: 递归扫桥后设备
- 7522-7528: `PcieInitLink(dev)` 才调用

### 验证优先级
1. 证明 BDS reset 链是否真的发生
2. 证明首轮扫描时 link 还没 ready
3. 检查 `DoPrepController()` 板级 hook
4. 检查 setup var 差异

### 建议加日志点
- `BdsProceedToBootCallback()` 入口、`ResetRequired`、CMOS `0x66`
- `EnumerateBus()` 里 NVMe 上游 port 的 VID/DID 返回值
- `PcieDoubleCheckCard()` 是否进入
- `PcieInitLink()` 调用前后

### Hypothesis Verifier 最终结论 (按置信度排序)

**1. 高置信度: NVMe ready 太慢，retry 路径太窄**
- `PciBus.c:6943-6992` 只有 `id==0xFFFFFFFF` + PCIe + dev0/fun0 + `SlotImpl==1` 才进 retry
- `AmiPciExpressLib.c:117-176` `PcieDoubleCheckCard()` 默认 5×1000us = 几毫秒
- M.2 常见 `SlotImpl=0` 或 `PresenceDet=0`，retry 根本不走

**2. 高置信度: 链路初始化在扫描之后，无 rescan**
- `PciBus.c:7407-7413` 先递归 `EnumerateBus()` 扫子总线
- `PciBus.c:7522-7527` 后调用 `PcieInitLink()`
- 没有"链路起来后重新扫描"机制，rescan 只在 OOR 场景触发

**3. 中置信度: PCIe setup 默认值偏激进**
- 清 CMOS 后首轮使用默认 setup 值
- `LnkTrRetry/LnkTrTimeout/LnkDisable/DontTouch` 可能不合适

**4. 低置信度: 枚举到了但没被用起来**
- 如果首轮已到 `InstallPciDevice()`，问题在 NVMe DXE/BDS 层

**5. 旁证: warm reset 改善硬件 ready**
- "冷启不行，warm 后好" 说明不是资源问题
- 本地 `Bds.c:1767-1836` 已有 first-boot warm reset 路径

### 已整理的知识点

1. **UEFI 启动流程概览**
   - SEC 阶段: Reset Vector (0xFFFFFFF0)、CAR 创建、PEI Foundation 调用
   - PEI 阶段: PEIM 调度、PPI 机制、HOB 传递、内存初始化
   - DXE 阶段: 驱动执行环境
   - BDS 阶段: 启动设备选择

2. **Cold Reset vs Warm Reset (CF9 寄存器)**
   - Warm Reset: `0x00 -> 0x06` (Soft Start -> Hard Reset)
   - Cold Reset: `0x02 -> 0x0E` (Hard Start -> Full Reset with power cycle)

3. **PCI 总线组成结构**
   - HOST 主桥、PCI 总线、PCI 桥、PCI 设备
   - 信号定义: AD[31:0]、PAR、C/BE[3:0]、RST#、INTA~D#

4. **PCIe BAR Size 与设备枚举**
   - BAR Size 最低要求随 PCIe 版本变化
   - EP 的 BDF 可以动态变化

5. **内存控制器**
   - 传统 vs 集成内存控制器
   - 内存时序参数: tCL、tRCD、tRP、tRAS
   - DDR 演进: SDR → DDR1 → DDR2 → DDR3

6. **M.2 PCIe 设备存在检测机制**
   - M2_CFG[3:0] 做模块识别
   - PCIe Link Training 做最终确认
   - 常见误区澄清

7. **PCIe Port 80h Decode**
   - Debug Port 设置可能影响设备枚举
   - DMI GCS 寄存器配置

## EmptyBridgeRecover Patch 验证结果 (18:48)

### 实验设计
Codex 实现了 `EmptyBridgeRecover` patch，在 `PciBus.c` 中添加桥恢复逻辑：
- `EmptyBridgeRecoverCheck()` - 检测空桥
- `EmptyBridgeRecoverReset()` - 执行 PCIe reset
- `EmptyBridgeRecoverRescan()` - 重新扫描

### 日志分析结果

**Cold 阶段 (失败)**:
```
B0:D1C:F4 首次 probe → 0xFFFFFFFF
    ↓
EmptyBridgeRecoverCheck/Reset 执行
    ↓
reset 后再次 probe → 0xFFFFFFFF
    ↓
EmptyBridgeRecoverRescan → Not Found
    ↓
后面走 InitLinkDisable
```

**Warm 阶段 (成功)**:
```
B0:D1C:F4 首次 probe → 0x576510EC (NVMe VID/DID)
    ↓
NVMe 正常安装协议并启动
```

### 关键结论
1. **Patch 命中了，但不够** - 恢复逻辑确实执行，挂点正确
2. **PcieResetLink() + rescan 在同一次 DXE 枚举里无法拉起 NVMe**
3. **Link 在 cold reset 后需要更长时间才能 ready**
4. **Warm reset 后设备已上电、链路已稳定，所以能被扫到**

### 代码位置索引
- 恢复函数: `PciBus.c:123`
- 调用点: `PciBus.c:7649`
- BDS cold reset: `Bds.c:1809-1825`

### 下一步建议
在 `EmptyBridgeRecoverReset` 后、`EnumerateBus()` 前打印：
- `LnkSta` - Link Status Register
- `DLLLA/LinkActive` - Data Link Layer Link Active
- `Training` - Link Training Status
- `Current Speed` - 当前链路速度

**二分判断**:
- `LinkActive=0` → reset 没把链路拉起来
- `LinkActive=1` 但 child 还是全 F → link 已起但 endpoint 还没 ready
