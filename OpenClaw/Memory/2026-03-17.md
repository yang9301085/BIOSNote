### 今日进展

#### 1. 深入分析 Cold/Warm Reset 差异

通过 Codex 会话深入分析了 CF9 寄存器机制：

**CF9 寄存器值**:
| 名称 | 值 | 作用 |
|---|---:|---|
| `SOFTSTARTSTATE` | `0x00` | 选择软启动状态 |
| `HARDSTARTSTATE` | `0x02` | 选择硬启动状态 |
| `HARDRESET` | `0x06` | 触发硬复位 |
| `FULLRESET` | `0x0E` | 触发全复位 (含 power cycle) |

**本平台实际路径**:
- `EfiResetWarm`: `0x00 -> 0x06`
- `EfiResetCold`: `0x02 -> 0x0E` (因 `COLD_RESET_WITH_POWER_CYCLE=1`)

#### 2. 建立 NVMe 首启异常工作模型

```
Cold Reset 路径:
BDS 检测首启 -> EfiResetCold -> CF9: 0x02 -> 0x0E
    ↓
M.2/PCIe 更接近"彻底冷起"状态
- 设备重新上电
- PERST#/REFCLK/CLKREQ# 重新走时序
- Root Port 重新训练链路
    ↓
如果任何一步不稳 -> PCI 枚举看不到 NVMe endpoint

Warm Reset 路径:
Shell/键盘触发 -> EfiResetWarm -> CF9: 0x00 -> 0x06
    ↓
平台/设备保留更多"非彻底冷起"状态
    ↓
M.2 SSD 更容易被枚举
```

#### 3. 关键澄清

- `SOFTSTARTSTATE` ≠ `SOFTRESET` (前者只是选状态，不触发复位)
- Cold Reset ≠ G3 掉电上电
- `gAmiNvmeControllerProtocolGuid` 丢失只是表象，根因在 PCIe 枚举层

### 新增知识点

#### M.2 PCIe 设备存在检测机制

**核心结论**: M.2 不是靠单根"设备存在引脚"判定，而是两层：
1. **模块识别**: `M2_CFG[3:0]` 编码识别模块类型/主接口
2. **最终确认**: PCIe Link Training 成功才算设备存在且可用

**关键引脚作用**:
- `M2_CFG[3:0]`: 最接近静态插入识别
- `CLKREQ#`: 时钟请求/电源管理，非 presence
- `PERST#`: 主机控制复位，不能反推有无设备
- `WAKE#`: 唤醒事件，平时无动静

**常见误区**:
- M.2 ≠ 标准 PCIe 插槽 (没有 `PRSNT#`)
- `CLKREQ#` 不是 presence detect
- `CFG[3:0]` 是模块类型编码，不是 Link Up 结论

**调试检查顺序**:
1. 静态层: CFG 采样、供电、PERST# 时序、REFCLK、CLKREQ# routing
2. 链路层: LTSSM 状态、Receiver Detect、Link negotiation、VID/DID
