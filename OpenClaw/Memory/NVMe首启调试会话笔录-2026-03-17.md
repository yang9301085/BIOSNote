## 二、根因分析

### 2.1 首启自动 Reset 机制

BDS 在启动前检测到首启 + runtime memory type 变化时，会自动发起 `EfiResetCold`：

```
开机 N
│
├─ PEI / DXE IPL
│  ├─ 从变量里取 EFI_MEMORY_TYPE_INFORMATION
│  ├─ 按这份配额建立内存类型信息
│  └─ 把结果放进 HOB 传给 DXE/BDS
│
├─ DXE / BDS
│  └─ 注册 "快要启动前" 的回调
│
├─ BeforeBoot 回调触发
│  └─ BdsProceedToBootCallback()
│     └─ SaveMemoryTypeInformation()
│
├─ SaveMemoryTypeInformation() 里做 4 件事
│  │
│  ├─ 1. 探测 PreviousMemoryTypeInformation
│  │    ├─ 找不到 -> IsFirstBoot = TRUE
│  │    └─ 找得到 -> IsFirstBoot = FALSE
│  │
│  ├─ 2. 保存"本次启动看到的旧表"
│  │    └─ 写 PreviousMemoryTypeInformation
│  │
│  ├─ 3. 统计本次真实内存使用量
│  │    └─ UpdateMemoryUsageInformation()
│  │       算出"下次启动应该用的新配额"
│  │
│  └─ 4. 如果新配额和旧配额不同
│       ├─ 写回 EFI_MEMORY_TYPE_INFORMATION
│       └─ 如果：
│          - IsFirstBoot == TRUE
│          - PcdResetOnMemoryTypeInformationChange == TRUE
│          - 改动涉及 runtime memory type
│          则 ResetRequired = TRUE
│
├─ 回到 BdsProceedToBootCallback()
│  ├─ 如果 ResetRequired == TRUE
│  └─ 调 pRS->ResetSystem(EfiResetCold)
│
└─ 开机 N+1
   ├─ PEI / DXE IPL 再次启动
   ├─ 这次一开始就读到"新"的 EFI_MEMORY_TYPE_INFORMATION
   ├─ 按新配额重新建立早期内存布局
   └─ 新配额终于真正生效
```

**代码位置**:
- "是不是首启"的判断: `Bds.c:1642`
- 写 `PreviousMemoryTypeInformation`: `Bds.c:1659`
- 重算新配额: `Bds.c:1698`
- 满足条件时置 `ResetRequired`: `Bds.c:1766`
- 最终发起 `EfiResetCold`: `Bds.c:1822`

### 2.2 Cold Reset vs Warm Reset 的硬件差异

#### CF9 寄存器值定义

| 名称 | 值 | 作用 | 会不会立刻复位 |
|---|---:|---|---|
| `SOFTSTARTSTATE` | `0x00` | 选择"软启动状态" | 不会 |
| `HARDSTARTSTATE` | `0x02` | 选择"硬启动状态" | 不会 |
| `HARDRESET` | `0x06` | 触发硬复位 | 会 |
| `FULLRESET` | `0x0E` | 触发更重的全复位 | 会 |

#### 实际 Reset 路径

**Warm Reset 路径** (`EfiResetWarm`):
```
SOFTSTARTSTATE (0x00) -> HARDRESET (0x06)
```
- 代码位置: `AmiSbMiscLib.c:227`
- 先设 `SOFTSTARTSTATE`，再发 `HARDRESET`

**Cold Reset 路径** (`EfiResetCold`):
```
HARDSTARTSTATE (0x02) -> FULLRESET (0x0E)
```
- 代码位置: `AmiSbMiscLib.c:234`
- 因为 `COLD_RESET_WITH_POWER_CYCLE=1` (见 `Sb.sdl:3441`)
- 先设 `HARDSTARTSTATE`，再发 `FULLRESET`

## 三、关键结论

### 3.1 核心因果链

```
变量里没历史记录
-> 认为是首启
-> 本轮统计到 runtime memory 配额要调整
-> 当前这轮已经太晚，不能现场改早期内存布局
-> 先写变量
-> cold reset
-> 下一轮从 PEI 开始按新配额重来
```

### 3.2 Cold Reset vs Warm Reset 本质区别

| 维度 | Warm Reset | Cold Reset |
|---|---|---|
| CF9 序列 | `0x00 -> 0x06` | `0x02 -> 0x0E` |
| 起始状态 | Soft Start State | Hard Start State |
| 复位类型 | Hard Reset | Full Reset (含 power cycle) |
| 设备状态 | 保留更多前提状态 | 更彻底清状态 |
| NVMe 表现 | 容易枚举成功 | 容易丢盘 |

### 3.3 重要澄清

1. **`SOFTSTARTSTATE` ≠ `SOFTRESET`**
   - `SOFTSTARTSTATE (0x00)` 只是选择起始状态，不会触发复位
   - 平台的 warm reset 实际是 `0x00 -> 0x06`，不是直接写 `0x04`

2. **Cold Reset ≠ G3 掉电上电**
   - Cold reset 更接近"从更干净的初始状态重来"
   - 但不等于严格意义上的 G3 掉电上电
   - 某些 always-on 域、resume well 是否真的掉下去，要看板级电源和 reset wiring

3. **`gAmiNvmeControllerProtocolGuid` 丢失只是表象**
   - 根因在 PCIe/M.2 枚举层
   - PCI 枚举阶段就看不到 NVMe endpoint
   - NVMe driver 没有 PciIo 可以 bind

## 四、下一步调查方向

### 4.1 需要验证的假设
- PERST# / REFCLK / CLKREQ# / 链路训练是否稳定
- Root Port 在 cold reset 后的状态

### 4.2 建议的调试手段
1. **寄存器检查**: 在 cold reset 后检查 Root Port 状态寄存器
2. **示波器测量**: PERST#、REFCLK、CLKREQ# 信号时序
3. **PCIe 链路训练**: 检查 Link Training 状态

### 4.3 可能的解决方案
- 检查 M.2 插槽的电源时序
- 检查 PERST# 信号的上拉/下拉
- 检查 PCIe 链路训练的等待时间
- 考虑在 PEI/DXE 阶段增加 PCIe 设备初始化的延迟
