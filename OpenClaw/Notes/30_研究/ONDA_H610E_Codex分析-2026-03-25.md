## 一、AmiModulePkg\Flash 模块运行时机

**核心结论**：`AmiModulePkg\Flash` 不是单一可执行模块，而是 PEIM / DXE_DRIVER / DXE_RUNTIME_DRIVER / BASE Library 的集合，按阶段分三路被链接：

| 库 | 链接进 | 阶段 |
|---|---|---|
| `SpiFlashAddressLib` (BASE) | `ICHxCspSpiFlashLib/PeiLib/SmmLib` 三套库 | PEI + DXE + SMM 共享 |
| `AmiFlashLibPei.inf` (PEIM) | FV_MAIN | PEI 阶段 |
| `FlashDriver.inf` (DXE) | FV_MAIN, Apriori_Index=2 | DXE 早期 |
| `AmiFlashLibSmm.inf` (SMM) | SMM Region | SMM 阶段 |

**关键条件**：`PCH_EXTENDED_BIOS_DECODE_ENABLE=1` 才会用真库，否则绑 Null 实现。

**运行时机**：上电后硬件 SPI 解码先行，BIOS 代码区在 `0x00400000..0x00FFFFFF`（16MB Flash，BIOS 区 12MB）。

## 二、SPI Flash 识别链路（SpiIdentify.c）

**作用**：SPI 通路成功 ≠ 知道"哪颗芯片"，`SpiIdentify.c` 确认芯片型号并加载对应规则表。

**完整识别流程**：
```
FlashInit() → SpiIdentify.c 遍历 gFlashList[]
  → CommonSpiReadId() → JEDEC Read ID (0x9F)
  → 按 ID 匹配: IdentifyStm_25PExx() / IdentifySst_25VF() 等
  → 填 gExFlashPart: FlashCommandMenu / FlashVenDevId / 容量/页大小/擦除粒度
  → ReinitializeSpiEnvironment()
  → ProgramVsccByDescriptor() → 写 BiosLVscc / BiosUVscc
```

**备用路径**：Descriptor VSCC 没匹配上 → `ProgramVsccBySfdp()` 用 SFDP 合 成 VSCC。

## 三、PEI Debug Log 中断根因分析

**现象**：`Wed-15-07-50.log` 停在 `StatusCodePei` 安装 `AmiDebugService` 之后，后续 DEBUG() 不再输出。

**根因**：不是"代码没跑"，而是 DEBUG() 路由被切走了：

```
AmiDebugService 安装后
  → DEBUG() 改走 gAmiDebugServicePpiGuid (PeiAmiDebugLib.c:94)
  → DebugService->Debug(...) → AmiDebugServiceDebugPrintHelper()
  → PeiDebugServicePrint (eLink parent, 签名: EFI_STATUS Func(CHAR8*, UINTN ErrorLevel))
  → PeiReportStringStatus (eLink parent, 签名: EFI_STATUS Func(VOID*, CHAR8*))
```

**真正缺失的环节**：`STRING_STATUS_SUPPORT = 0` → `PEI_STRING_LIST` 为空 → `SerialOutput` 未被链接 → 串口断流。

**修复方向**：`PeiDebugServicePrint` 不能直接接 `SerialOutput`（签名不匹配），正确路径是 `PeiReportStringStatus -> SerialOutput`，需要打开 `SERIAL_STATUS_SUPPORT` token。

## 四、三路 Debug 体系（Serial / USB3 / TraceHub）

这是三层并存的体系，不是三选一：

| Debug 类型 | 平台选择层 | 固件输出层 | 当前状态 |
|---|---|---|---|
| **Serial UART** | Setup / SDL / PCD | `AmiModulePkg/AmiStatusCode` → `SerialOutput` | ✅ 生效 (`SERIAL_STATUS_SUPPORT=1`) |
| **USB3 Debug** | `PcdUsb3SerialStatusCodeEnable` | `Usb3DebugPortLib` (当前空实现) | ❌ 空实现 |
| **TraceHub** | `PcdStatusCodeUseTraceHub` | `TraceHubStatusCodeHandler` (Pcd 为 0) | ⚠️ 库已编入但 PCD 未开 |

**包边界**：
- `A5Debugger` = host 侧调试工具（不是 BIOS 固件模块）
- `AMIDebuggerPkg` = BIOS 侧 debugger agent / transport 栈（可替代 AmiStatusCode）
- `AmiModulePkg/AmiStatusCode` = 框架/分发器，不是完整 debugger

## 五、debugLog.log 四启动周期分析

**日志切分**（4 个启动周期，模式重复两遍）：
- Boot #1: CMOS_BAD_CHECKSUM + Battery BAD → ME 要求 warm reset → **ResetSystem.c(282) assert**
- Boot #2: 跟随启动，`WarmRstReqForDF=0`，正常继续
- Boot #3: 手动 clear CMOS，重演 Boot #1
- Boot #4: 再次跟随启动，正常继续

**两次重启触发机制**：
- 根因：`PchMeUma.c` 的 `CpuReplacementCheck()` / `HandleMeBiosAction()` 检测到 `WarmRstReqForDF=1`
- ME FW DID ACK 请求 Non Power Cycle Reset（不是掉电复位）
- `ResetSystem.c(282)` assert 的回调最可能是 `WdtResetNotificationCallback`（高置信）

**关键文件**：
- `ResetSystem.c:282` — 断言点
- `PchMeUma.c` — ME/DF warm reset 请求
- `TpvPei` — WDT reset notification 所属 PEIM

## 六、VSCC Table 角色

**作用**：Flash Descriptor 里的 Vendor Specific Component Capabilities 表，按 JEDEC ID 绑定 SPI 控制器能力参数，写入 `BiosLVscc / BiosUVscc`。

**当前项目 VSCC 条目**：`VEN25QX128ID`（WEN25QX128 对应 Winbond W25Q128JV）
